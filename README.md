# Vehicle complaints: QLoRA fine-tuning vs baselines, and HF vs vLLM serving

[![CI](https://github.com/juhidixit/vehicle-complaints-lora-vllm/actions/workflows/ci.yml/badge.svg)](https://github.com/juhidixit/vehicle-complaints-lora-vllm/actions/workflows/ci.yml)

Two questions, answered with measurements on public data:

1. **Is fine-tuning a small open LLM worth it** for routing US vehicle-safety complaints to the
   failed component, compared with a TF-IDF classifier and with prompting the same LLM?
2. **What does serving that model cost**, with Hugging Face Transformers vs vLLM, 16-bit vs
   4-bit, and a merged model vs a hot-swapped LoRA adapter?

Every number in the tables below is generated by `report/make_report.py` from the JSON files in
[`results/`](results/). Tables that still say _Not run yet._ have not been measured, and nothing
is estimated in their place.

## Problem

NHTSA's Office of Defects Investigation receives tens of thousands of consumer complaints a year.
Each one is a free-text narrative written by a vehicle owner, plus the component the owner
selected (`COMPDESC`). Routing a narrative to the right component is a realistic triage task
for defect investigators and manufacturers' field-quality teams, and it is a clean, closed-label
benchmark for comparing fine-tuning with prompting.

- **Input:** the complaint narrative (`CDESCR`), truncated to 250 words.
- **Label:** the top-level component (text before the first `:` of `COMPDESC`), 10 classes.
- **Headline metric:** macro-F1, so small components count as much as large ones. Accuracy,
  per-class F1 and confusion matrices are also reported, with 95% bootstrap confidence
  intervals over test examples (1,000 resamples).
- **Two test sets:** a stratified held-out test set from the same years as training, and a
  **time-shift** test set from the most recent full year, which the models never saw.

## Data card

Public-domain US government data: the NHTSA complaints flat file
(`FLAT_CMPL.zip`, layout in NHTSA's `CMPL.txt`). Raw data is not committed; the complaint IDs of
every split are, in [`data/splits/`](data/splits/), so the exact splits can be rebuilt with
`make data-from-ids`.

How the splits are built ([`data/build_splits.py`](data/build_splits.py)):

1. Check our field order against NHTSA's layout document; stop if it differs.
2. Group flat-file lines by complaint ID (`ODINO`); one line is one (complaint, component) pair.
3. Keep complaints that name exactly one top-level component (the main task is single-label),
   excluding `UNKNOWN OR OTHER`, which is not a component.
4. Drop narratives under 20 words. De-duplicate by exact narrative text (case-insensitive);
   copies that disagree on the label are all dropped.
5. Main pool: complaints received in the 10 years before the latest full year. Keep the 10 most
   frequent components. Sample 24,000 complaints keeping label proportions, then split
   20,000 / 2,000 / 2,000 (train / validation / test), stratified, seed 13.
6. Time-shift test: 2,000 random complaints received in the latest full year, same 10 labels,
   with that year's own label mix.

## Systems compared

| System | What it is |
|---|---|
| Majority class | Always predicts the most frequent training label |
| TF-IDF + logistic regression | Word 1-2-grams, sublinear TF; `C` and class weighting picked on the validation split only |
| Zero-shot | `Qwen/Qwen2.5-1.5B-Instruct` with the closed label list in the system prompt |
| 5-shot | Same, plus 5 training examples with distinct labels (fixed seed) as chat turns |
| QLoRA fine-tuned | Same model and prompt, fine-tuned on the 20,000 training examples |
| QLoRA, W4A16 | The fine-tuned model merged and quantized to 4-bit weights with GPTQ |

All LLM systems use the same system prompt and greedy decoding. Output is mapped to the closed
label list ([`src/vclora/prompting.py`](src/vclora/prompting.py)); anything that does not map to
exactly one label counts as wrong, and its rate is reported as "Unparseable".

QLoRA settings ([`train/config.yaml`](train/config.yaml)): 4-bit NF4 base with double
quantization, LoRA r=16, alpha=32, dropout 0.05 on all linear layers, learning rate 2e-4 with
cosine decay and 3% warm-up, 2 epochs, effective batch 16, max length 512, paged 8-bit AdamW,
loss on the answer tokens only (TRL prompt-completion format).

## Reproduce

CPU part (data, classic baselines, report), on any machine with internet access:

```bash
pip install -e ".[dev]"
make data          # download NHTSA file, check layout, build splits (or: make data-from-ids)
make baselines     # majority + TF-IDF/LR
make report        # regenerate README tables and charts from results/
```

The same CPU part runs on GitHub Actions: **Actions → data-and-baselines → Run workflow**.

GPU part, on one NVIDIA GPU (tested path: the notebook in [`notebooks/gpu_pipeline.ipynb`](notebooks/gpu_pipeline.ipynb),
which runs on Kaggle or on a rented GPU with Jupyter):

```bash
pip install -e ".[gpu,dev]"
make data-from-ids         # rebuild the committed splits
make llm-baselines         # zero-shot and 5-shot
make train SEEDS="0"       # QLoRA; SEEDS="0 1 2" for three seeds
make eval                  # merge adapter, score fine-tuned model
make quantize              # GPTQ W4A16 + score it
make bench                 # offline + server load tests
make report
```

`make all` runs everything in order.

## Limitations

- **Single-component complaints only.** Complaints naming several components are dropped, so
  the task is easier than real triage, which is multi-label.
- **Labels are consumer-written.** The component is chosen by the person complaining, so some
  labels are wrong or ambiguous (for example engine vs power train). No model can score
  100% here, and part of the remaining error is label noise.
- **One GPU type** per run. Throughput and cost numbers do not transfer directly to other GPUs.
- **One base model size** (1.5B). Larger models would do better zero-shot.
- **Prices are inputs.** Cost per 1,000 depends on the hourly price entered in `bench/prices.yaml`.
